## 一、必须拍板的 5 个岔路

### D1 · WebFlux（响应式）与 MyBatis（阻塞 JDBC）的模型冲突 ⚠️ 最高优先级

**问题**：WebFlux 的事件循环（EventLoop）线程数 = CPU 核数，一旦在 EventLoop 上执行 MyBatis 的阻塞 JDBC 调用，会直接拖垮整个服务的吞吐，这是选型里最硬的一处冲突。

**默认选择：Kotlin 协程 + 调度器卸载（保留 WebFlux + MyBatis）**

```
HTTP 请求 → EventLoop(Netty) → coRouter(suspend) → withContext(Dispatchers.IO) → MyBatis(JDBC) → 回到 EventLoop 写响应
```

- 用 `coRouter { }` + `suspend` 函数写业务代码，**代码形态与同步写法一致**，可读性接近 Spring MVC；
- 在 Repository 实现层统一用 `withContext(Dispatchers.IO.limitedParallelism(N))` 把 JDBC 阻塞调用卸载到专用线程池，EventLoop 不被占用；
- `N`（IO 并发度）与 HikariCP 连接池大小对齐，例如连接池 50 则 `limitedParallelism(50)`，避免"线程等连接"的无效排队。

**为什么不全链路响应式（R2DBC）**：本系统是交易型系统，复杂动态 SQL、多表关联、分页是常态，R2DBC 在这些场景下生态与调试成本显著高于 MyBatis，且 MyBatis 的租户/数据权限拦截器方案成熟，自研 R2DBC 版拦截器工作量翻倍。

**推翻代价**：
- 改全链路 R2DBC → 持久层全部重写，`01`/`02` 中的权限拦截器需另写 R2DBC 版（工作量约 +40%），表结构**不受影响**；
- 改回 Spring MVC（放弃 WebFlux）→ 目录结构基本不变，**删掉协程层即可，代价很小**，且性能对本项目（万级租户、非超高并发）反而更匹配。
- 👉 **个人建议**：如果团队没有响应式编程经验，**直接换 Spring MVC 是更务实的选择**，本套权限模型与表结构完全兼容，无需改动。

### D2 · 多租户隔离粒度

**问题**：全国行政村约 50 万个、农贸市场数万个，租户量级是"十万级、单租户数据量小"。

**默认选择：共享库 + 共享表 + `tenant_id` 列**

- 所有业务表强制带 `tenant_id bigint not null`，配合 `(tenant_id, ...)` 复合索引；
- 隔离由**应用层拦截器强制注入**（见 D3），任何 SQL 都不可能漏掉租户条件（拦截器是兜底，不是可选）；
- 额外启用 PG **Row Level Security（RLS）** 作为**第二道保险**，防止应用层被绕过（如 DBA 直连、脚本误操作、未来引入的 BI 工具）。

**为什么不用独立 Schema / 独立库**：十万级 schema 会让迁移（DDL 变更）变成灾难，连接池与元数据开销也不可接受；独立库更不可能。

**推翻代价**：表结构**基本不受影响**（`tenant_id` 始终存在），切换 schema 隔离主要是运维侧的脚本工作。

### D3 · 数据权限落地方式

**默认选择：MyBatis 拦截器自动改写 SQL（对业务代码零侵入）**

- 定义受保护资源 `sys.data_object`（哪张表、租户列/组织列/归属人列叫什么）；
- 定义系统级策略 `sys.data_scope_policy`（范围类型 + 表达式）；
- 拦截器在 `Executor#query` 阶段解析 SQL 的**表别名**，自动追加 `AND alias.tenant_id = ? AND (alias.org_id IN (...) OR alias.created_member_id = ?)`；
- 范围类型：`GLOBAL` / `TENANT_ALL` / `ORG_SELF` / `ORG_TREE` / `MEMBER_SELF` / `MEMBER_TEAM` / `CUSTOM_SQL`。

**为什么不用 PG 原生 RLS 做主力**：RLS 策略写在数据库里，动态规则（按角色、按人、按时间）维护与调试困难，且难以做"多策略叠加 + 优先级"。本项目把它降级为**兜底防线**（只做最粗的 `tenant_id` 隔离），主逻辑仍在应用层。

**推翻代价**：小。RLS 与拦截器可以共存，改主力只需调整拦截器开关。

### D4 · "数据权限是系统级配置" 与 "角色是租户自定义" 的边界

**这是文档里最模糊的一条，我做如下解读，请确认：**

| 层级 | 由谁定义 | 由谁分配 | 落表 |
|---|---|---|---|
| **功能权限** Permission | 系统（随应用打包发布，代码里声明） | 租户管理员，通过**租户自定义角色**分配给成员 | `sys.permission` → `sys.role_permission` → `sys.member_role` |
| **数据权限** DataScope | 系统（预置策略模板，不可由租户新建） | **超级管理员**（把系统级策略绑定到角色/成员） | `sys.data_scope_policy` → `sys.data_scope_binding` |
| **应用可见范围** | 系统（租户类型 ↔ 应用） | 系统 + 租户开通 | `sys.tenant_type_app` |

即：**租户只能在系统给定的策略清单里"套用"，不能自己发明新的数据范围规则**。这符合"数据权限作为系统级配置，交给超级管理员处理"的表述。

**待确认**：数据范围策略是否允许租户管理员在**自己租户内**调整（例如把"仅本人"放宽到"全租户"）？
- 我的默认：**允许，但只能从超管授予的最大范围内收窄，不能放大**（`max_scope` 字段控制）；
- 若你要求"租户完全不能碰数据权限"，则移除 `sys.data_scope_binding.tenant_id` 相关逻辑即可。

---

### D5 · 超级管理员的定位

**默认选择：超管是"系统配置账号"，不是"业务账号"**

- `sys.user_account.user_kind = 'SUPER_ADMIN'`，由初始化 SQL 内置，**不可删除、权限不可回收**；
- 不隶属于任何业务租户（`sys.member` 中无记录），仅绑定全局角色 `sys.user_global_role`；
- 拥有全部应用全部功能权限，数据范围恒为 `GLOBAL`，**绕过所有租户角色校验**；
- 登录时无需选择租户，直接进入系统管理后台；
- 租户内部的最高权限者是"租户管理员"（`sys.member.is_tenant_admin`），**不是超管**。

**待确认**：
1. 是否需要"二级超管"（如省级运营管理员，只能管本省租户）？→ 默认不提供，需要则用 `GLOBAL` + `REGION` 数据范围策略实现；
2. 超管能否代登租户处理业务？→ 默认**禁止**（审计风险极高），如需支持必须走 `sys.audit_log` 全量留痕 + 双人审批。

## 二、我做的技术假设（如与现状不符请指出）

| # | 假设 | 如不成立的影响 |
|---|---|---|
| A1 | Spring Boot 4.1.1 已发布且基于 Spring Framework 7，JDK 21 基线 | 版本号在 `libs.versions.toml` 中集中管理，改一处即可 |
| A2 | `mybatis-spring-boot-starter` 有兼容 Boot 4 的版本 | **需实测**。若不兼容，降级到 MyBatis 原生 `SqlSessionFactory` + 手动装配（配置文件中已给出兜底写法） |
| A3 | 微服务用 Spring Cloud（Gateway + Nacos/Consul 注册中心） | 若自建 K8s Service 直连，删除 gateway 的 lb 配置即可 |
| A4 | 认证用 JWT（无状态）+ Redis 存租户上下文与权限快照 | 若要求强会话管控（可踢下线），改为 Redis 会话令牌，改动集中在 `agri-auth` |
| A5 | 组织维度只有"租户内组织树"一层（`sys.org`），租户之间不做层级 | 文档提到"化肥农药厂或代理商"，若代理商有下级代理，需启用 `sys.tenant.parent_id` + `tenant.path`，DDL 已预留 |
| A6 | 前端 Vue 3 + Vite + TypeScript + Pinia，pnpm 单仓多应用（monorepo） | 若多仓独立部署，`03`/`04` 目录按应用拆分即可，权限 SDK 需独立发包 |
| A7 | 系统只做交易撮合与确认，不落资金流水，因此**不设计账户/支付/对账表** | 若后续加资金，需新增独立的 `pay` 域，不污染现有权限模型 |

## 三、明确不做的事（避免过度设计）

- ❌ 不做 SSO 单点登录（如需，在 `agri-auth` 增加 OIDC 客户端即可，权限模型不变）
- ❌ 不做字段级权限（`sys.data_object` 预留了 `column_mask` 字段但未启用，真有需求再开）
- ❌ 不做审批流（角色授予默认即时生效；如需审批，在 `sys.member_role` 加 `status + approve_by`）
- ❌ 不做权限的生效时间段（`effective_from/effective_to` 字段已预留，默认不校验）
